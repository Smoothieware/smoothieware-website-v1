# K-type thermocouple interface

A MAX31855KASA reads a K-type thermocouple and exposes temperature/fault data over a read-only SPI-style interface. It is for thermocouples, not thermistors or PT100 probes. A practical use is monitoring a K-type machine temperature before deciding whether to control a heater.

## Documented source and compatibility

This guide describes the [retained original Smoothieboard2 source](https://github.com/Smoothieware/Smoothieboard2/tree/52ab340de33180a975b25f856c161993488e6ace/extensions/Thermocouple), not a modern board with a similar purpose. The original host generation predates Smoothieboard V2 Prime. Connector compatibility must be established contact by contact. Production, assembly availability and physical testing are not established by these files.

## Power, signals and controls

Use a K-type thermocouple with **P1.1 = T−** and **P1.2 = T+**. The matching cached MAX31855 symbol identifies U1.2 as T− and U1.3 as T+; the retained netlist connects them to P1.1 and P1.2 respectively. C2 bridges these two signal nets as a differential filter; it is not a series connection. Do not infer polarity from cable colour without the probe manufacturer's colour standard.

P2.1 supplies +3.3 V and P2.10 is ground. P2.8 carries the U1.7 serial output toward the host. Clock enters P2.9 through D2 and chip select enters P2.6 through D1. In both 1N4148 symbols, contact 1 is the cathode on the host side; contact 2 is the anode on the MAX31855 side. R2 and R1 pull the chip-side clock and chip-select nets up to +3.3 V. These are diode/pull-up paths, not copper-equivalent direct wires: their low-level voltage and rise-time margin at the driver's fixed clock remain unqualified. This source does not establish permission to power the board from 5 V.

The retained [MAX31855 data sheet, revision 5](https://www.analog.com/media/en/technical-documentation/data-sheets/max31855.pdf) specifies a 3.0–3.6 V operating supply, a logic-low maximum of 0.8 V and logic-high minimum of 2.1 V. Its interface permits at most 200 ns clock rise/fall time and requires at least 100 ns high/low pulse widths. These are **chip requirements**, not qualified performance of this board. Check the voltage at the chip-side diode anodes and the pull-up rise time, including board/cable capacitance; a 1 MHz host clock alone does not establish compliance. The retained copy is revision 5 (January 2015); no later revision is claimed here.

### Annotated connector and component reference

These newly source-derived drawings retain the selected native outline, footprints, pads and graphics with function callouts. They are not a recovered canonical abstract or a verified mating view. The MAX31855 source and manufacturer pin map identify U1.5 as SCK and U1.6 as active-low CS: P2.9 reaches U1.5 through D2, and P2.6 reaches U1.6 through D1. This does not qualify the complete SPI or thermocouple installation. Host allocation, firmware and powered operation remain unqualified.

## Connect and try it

The following is a **source-derived connection candidate**, pending electrical qualification of the diode/pull-up control paths and physical cable orientation. It is not an accepted plug-in cable. Prime's GE/J36 header exposes the SPI1 signals used by firmware channel 0; the older S header is not interchangeable with arbitrary Prime headers.

| Prime V2 Prime GE/J36 contact | Historical board contact | Function and direction |
|---|---|---|
| 1, limited 3.3 V | P2.1 | Host supply → board; available current budget still needs checking |
| 10, ground | P2.10 | Common return |
| 8, PA6 / SPI1 CIPO | P2.8 | MAX31855 serial data → host |
| 9, PA5 / SPI1 clock | P2.9 | Host clock → D2/pull-up → U1.5 |
| 6, PD15 | P2.6 | Reserved host output → D1/pull-up → U1.6 active-low chip select |

Leave historical P2.2–5 and P2.7 unused. No host-to-sensor data line is required. Reserve PD15 and the SPI1 bus against other configured users before choosing this allocation. Connector numbers refer to native source contact numbers, not an assumed ribbon-cable stripe or mating-face view.

After electrical and orientation checks, start with an ambient-temperature probe and no heater connected. Verify plausible readings, then disconnect the probe and verify an invalid/fault response before relying on it. This is temperature monitoring; it does not establish a heater-control or safety system.

## Smoothieware use

The [pinned V2 application source](https://github.com/Smoothieware/SmoothieV2/blob/2a21c0108b1d095ecd8b2b9358e94055f053c003/Firmware/src/modules/tools/temperaturecontrol/max31855.cpp) parses **`spi_select_pin`**, `spi_channel` and `readings_per_second`. The internal C++ identifier `spi_cs_pin_key` is not the configuration spelling. Its driver initializes 16-bit SPI mode 0 at 1 MHz and requires all MAX31855 instances to share one channel. The matching Prime HAL maps channel 0 to SPI1: PB5 output, PA6 input and PA5 clock.

Once the conditional connection above is qualified, this is the corresponding **monitor-only configuration candidate**. It verifies parser syntax and source-selected pins; it is not a claim that the historical board has been tested at 1 MHz:

```ini
[temperature control]
tc_monitor.enable = true
tc_monitor.sensor = max31855
tc_monitor.spi_channel = 0
tc_monitor.spi_select_pin = PD15
tc_monitor.readings_per_second = 20
tc_monitor.heater_pin = nc
tc_monitor.designator = TC
```

`heater_pin = nc` makes this instance read-only. Use a unique instance name and designator if other temperature sensors exist. Issue `M105` to request temperature reports. In this source, invalid/infinite sensor data is printed as `-100`; that sentinel is not a measured −100 °C temperature. Do not use a plausible-looking number alone as evidence that probe polarity, bus wiring or fault detection is correct.

Firmware claims are bound to commit `2a21c0108b1d095ecd8b2b9358e94055f053c003`; Prime connector claims use P12 Prime source commit `7dc4f9a972ad3e3587952171e63b278ee9997f10`. Source inspection is not a target build, flash, boot or hardware result. A MAX31855 driver exists in the inspected source. If required support is absent in your firmware, email **wolf.arthur@gamil.com**.
