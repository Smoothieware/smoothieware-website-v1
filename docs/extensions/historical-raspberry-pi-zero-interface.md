# Raspberry Pi Zero carrier interface

This carrier connects a Pi Zero’s GPIO/UART to an earlier Smoothieboard2 host connector and provides a regulator and serial indicator circuitry. Unlike the separate Ethernet record, this source does not contain the ENC28J60 Ethernet controller.

## Documented source and compatibility

This guide describes the [retained original Smoothieboard2 source](https://github.com/Smoothieware/Smoothieboard2/tree/52ab340de33180a975b25f856c161993488e6ace/extensions/Rpi-zero), not a modern board with a similar purpose. The original host generation predates Smoothieboard V2 Prime. Connector compatibility must be established contact by contact. Production, assembly availability and physical testing are not established by these files.

## Power, signals and controls

P3 is the 40-contact Pi interface; P2/P5 expose odd/even rows. P3.8/.10 are serial HTXSRX/HRXSTX, routed to P4.4/.5. P4.1 is /3v3-smoothie, while Pi supply is /3v3-pi; their differing net names must be respected. P1.1 is ground and .2 regulator input; U1 is R-78HB5.0-0.5L. D1/D2 form supply paths and D3/D4 the indicator circuitry. /Ground and GND are not automatically equivalent.

### Board functions and connector roles

Start with these four views of the selected historical Pi Zero carrier. The Pi header and GPIO breakouts share the Pi-side source nets; the host connector has a separate ground and 3.3 V rail. The two named UART paths identify source connectivity only: transmit/receive direction and a complete Prime cable remain unresolved. Do not bridge the ground domains or select a power connection from these reference drawings. Read the power and wiring qualifications below.

## Connect and try it

Use it as a candidate serial G-code companion after proving rail separation, ground continuity and correct UART direction. Pi physical contact numbers are not STM32 pin names. ### Practical Prime wiring diagram — pending

The serial directions can be traced to the selected native contacts. They require a crossover at the historical host connector:

| Direction | Smoothieboard V2 Prime | Historical carrier | Pi header |
|---|---|---|---|
| Prime sends to Pi | GB/J33 contact 4, PB9 TX | P4 contact 5, `/HRXSTX` | P3 physical contact 10, GPIO15 RX |
| Pi sends to Prime | GB/J33 contact 5, PH14 RX | P4 contact 4, `/HTXSRX` | P3 physical contact 8, GPIO14 TX |

**Do not use a same-numbered 4-to-4 / 5-to-5 cable:** that would join the two transmitters together. The [official Raspberry Pi UART documentation](https://www.raspberrypi.com/documentation/computers/configuration.html#configure-uarts) identifies GPIO14 as TX and GPIO15 as RX. These are 3.3 V logic signals, not RS-232 voltage levels.

This table is a source-traced signal allocation, not a complete powered installation. P4 contact 10 is `GND`, while the Pi-header returns are `/Ground`; the retained contact schedule does not establish their connection. Resolve the actual return path, indicator loading and unpowered-device behavior first. P4 contact 2 feeds one diode path and the regulator feeds another into Pi +5 V: neither Prime power rail is authorized by this tracing. Establish supply ownership, diode losses, current budget and backfeed behavior before connecting power. The complete practical diagram remains pending those connections.

## Smoothieware use

### Host setup still required

The Prime UART console is a supported software endpoint, but this historical interface has a source-traced serial crossover but still needs a qualified common return and power ownership before a cable can be documented. In the retained native source, Pi-header grounds use /Ground while the Gadgeteer return is GND; do not assume those named nets are joined. The historical interface still lacks a qualified loaded-signal/return/power contract, Pi model/image setup and actual indicator behavior; no plug-and-play support or complete installation is claimed.

### Configure the Prime serial command console

After the carrier’s return, power ownership and loaded logic levels are resolved, reserve Prime UART channel 1 and PB9/PH14 for this connection. Merge this section into the controller configuration, keeping only one definition of the console:

```ini
[uart console]
enable = true
console = true
channel = 1
baudrate = 115200
bits = 8
stop_bits = 1
parity = none
```

The [pinned console parser](https://github.com/Smoothieware/SmoothieV2/blob/2a21c0108b1d095ecd8b2b9358e94055f053c003/Firmware/src/Consoles.cpp#L733-L761) reads these seven settings. Channel 1 selects PB9 TX and PH14 RX in the UART HAL; it does not assign arbitrary GPIO. Use the crossed GB/J33 contacts in the table above. `console = false` would initialize an auxiliary UART without its command-console reader, so it is not the command-host setting shown here.

Configure the actual Pi model and installed Linux image to expose the corresponding UART, release any conflicting Linux serial console, and use 115200 bit/s, 8 data bits, no parity, one stop bit, with hardware flow control off. The primary UART differs between Pi Zero variants: do not assume `ttyAMA0` for all models. Once the electrical prerequisites are met, send `version` followed by LF (`\n`). CRLF also works; CR alone is ignored and does not dispatch the command. The [registered version command](https://github.com/Smoothieware/SmoothieV2/blob/2a21c0108b1d095ecd8b2b9358e94055f053c003/Firmware/src/CommandShell.cpp#L1485-L1505) returns build information without requesting motion. Its response identifies the running build; it does not prove the carrier’s electrical qualification.
