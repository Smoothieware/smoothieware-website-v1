# SPI opto-isolator

Seven 6N137 optocouplers transport six host-to-peripheral signals and one return signal across separate power domains. This is a directional SPI/interface isolator, not an arbitrary bidirectional GPIO cable.

## Documented source and compatibility

This guide describes the [retained original Smoothieboard2 source](https://github.com/Smoothieware/Smoothieboard2/tree/52ab340de33180a975b25f856c161993488e6ace/extensions/SPIOpto), not a modern board with a similar purpose. The original host generation predates Smoothieboard V2 Prime. Connector compatibility must be established contact by contact. Production, assembly availability and physical testing are not established by these files.

## Power, signals and controls

The netlist calls the host/external connectors C2/C6, but the PCB labels them Conn1/Conn2. All ten signal/power net names correspond after that explicit reference rename; do not look for a physical capacitor C2 as the host socket. Host signals CS/MOSI/SCK/GPIO0/GPIO1/GPIO2 drive U1/U2/U3/U5/U6/U7; U4 carries MISO back. Host supply is +5V/GND, external supply External5V/ExternalGND. P1.1/.2 expose host ground/5 V; P2.1/.2 external ground/5 V. The six forward and one reverse paths must be checked for inversion and 3.3 V compatibility. In particular, the returned MISO net is pulled to host +5V through R8 (330 Ω); it must not be treated as a proven safe 3.3 V Prime input. Connecting the grounds and 5 V rails as the historical note permits defeats galvanic separation; no isolation voltage or safety qualification is established.

### Exact optocoupler and logic-drive limits

The selected bill of materials names **Lite-On 6N137S-TA1**. The [manufacturer-authored 6N137 Series datasheet](https://media.digikey.com/pdf/Data%20Sheets/Lite-On%20PDFs/6N137%20Series.pdf), transfer table on page 9, gives a maximum input threshold of 5 mA under its stated supply, enable and output-load conditions. A nominal `(3.3 V − typical LED voltage) / 330 Ω` calculation does not guarantee that current across loaded Prime output voltage, resistor tolerance and temperature. A generic 6N137 datasheet from another manufacturer does not establish this fitted part’s limits.

The same table specifies output LOW at up to 0.6 V under a 13 mA load and 5 mA input test condition. The native 330 Ω output pull-ups therefore also need rail/tolerance and receiver-load analysis. In particular, the host MISO pull-up remains connected to +5 V: do not connect that return directly to a Prime GPIO on the strength of the nominal SPI net names. Signal inversion, enable bias, timing and both isolated power domains must be resolved in a complete interface circuit.

### Board functions and contact reference

These source-derived sheets explain both connectors, all seven optocoupler channels and their supply/return contacts. All seven channels invert when enabled. The host MISO pull-up is 5 V; direct Prime compatibility is unqualified. Read every sheet for the selected component. The populated reconstruction is not a recovered canonical smoothie-diagrams abstract.

## Smoothieware use

### SPI transport: exact supported sensor contract, incompatible selected interface
The selected Lite-On6N137S-TA1 channels invert forward clock/data/CS and return MISO; the return output is pulled to host5 V. Do not substitute6N137-L limits or connect this return directly to Prime. Qualify loaded drive current, bias, inversion, timing and power order. Inverting CS alone cannot repair SCK/MISO polarity.

The transport has no register driver. For a separately qualified mode0/1 MHz MAX31855 interface, the real firmware settings are:

```ini
[temperature control]
transport_tc.enable = true
transport_tc.sensor = max31855
transport_tc.spi_channel = 0
transport_tc.spi_select_pin = PD15
transport_tc.readings_per_second = 20
transport_tc.heater_pin = nc
transport_tc.designator = XT
transport_tc.tool_id = 251
```

Prime GE/J36 SPI1 COPI/CIPO/SCK are contacts7/8/9 and PD15 is contact6; that defines the host bus allocation, not an accepted historical-board cable. After the entire adapted link and named sensor are qualified, `M105` observes XT and plain `M305` reports sensor diagnostics. No heater is driven. The driver fixes mode0 at 1 MHz and exposes neither lower clock nor data/clock inversion/CS-delay configuration; readings_per_second is polling, not bus frequency. The invalid sentinel-100 is not a measured temperature. This is an exact conditional sensor software contract, explicitly not a working selected-board recipe.

The selected seven-channel Lite-On 6N137S-TA1 circuit inverts its forward SCK/data/chip-select paths and return MISO path. The matching primary truth table establishes that enabled LED current produces LOW at the output; selected pin7 enable contacts are tied to each output-side supply. This is not a transparent non-inverting SPI cable.

At reviewed SmoothieV2 commit `2a21c0108b1d095ecd8b2b9358e94055f053c003`, the MAX31855 application initializes SPI as **16-bit, mode0, 1 MHz** in `max31855.cpp:38`. Its configuration parser accepts `spi_channel`, `spi_select_pin` and `readings_per_second`; it exposes no transport polarity, return-data inversion, clock-frequency or chip-select-delay setting. The read path consumes the returned sensor words without optocoupler-specific data inversion. A `!` on the chip-select pin only changes that pin and cannot correct SCK and MISO. Changing polling frequency does not change the SPI bit clock.

Thus the built-in MAX31855 settings printed above are **not firmware support for this selected inverting board**. The link-compatible polarity/timing adaptation required for that named use is absent from this reviewed MAX31855 implementation. Email **wolf.arthur@gamil.com** for the required matching support. Do not invent a `spi_mode`, `invert_data` or lower-frequency setting or connect a sensor merely because a MAX31855 driver exists.

This statement is scoped to the reviewed built-in MAX31855 application. It does not prove that no external fork, other application or separately designed hardware adapter exists. The selected 5 V host-side return, LED drive currents, loaded timing and power-order issues are separate electrical limitations. Implementing a polarity adapter alone would not make a direct Prime connection electrically acceptable. No working powered wiring, target/runtime or reader/viewer acceptance is claimed.
